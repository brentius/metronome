# SPEC_V2 ambiguities found while writing the Lean machine spec

Written 2026-11-20 by workstream A of `BOTS/PLANS/LEAN_MACHINE_SPEC_PLAN.md`. The sources were `wiki/SPEC_V2.md`, the SPEC v1 sections it cites, `wiki/ISA_TABLES_V2.md` and `code/md2/machine.{py,json}` (names and numbers only). The Python model, the RTL and the other Lean files were not read.

Each entry gives the clause, the reading the Lean takes, and the alternatives. The Lean marks the place with `-- AMBIG(n)`. Where the SPEC was silent, the Lean takes the most literal reading available. These are candidates for SPEC fixes, and for triage when the lockstep shows a mismatch.

| # | Clause | Lean reading | Alternatives | Where |
|---|---|---|---|---|
| 1 | §1 "`rst_n` is asserted asynchronously … `rst_q` is `rst_n` delayed by two rising edges" | `rst_q` is low in any cycle whose input `rst_n` is 0 (asynchronous assertion), so the state after that cycle is all zero. After release, `rst_q` is high from the second cycle after the first cycle with `rst_n = 1`. The synchronisers and the SPI link state are registers, so they reset too. | Assertion also delayed by two edges, as the phrase "delayed by two rising edges" says literally. The synchronisers might not be reset. | `Chip.resetStep`, `stepObs` |
| 2 | §1 "A configuration write in the two cycles after `rst_q` rises is ignored" | The two cycles are the first two with `rst_q` high. Any bank write performed in them is dropped. This cannot happen through SPI. | The cycles r+1 and r+2. A held write `HH` might also survive. | `Chip.runStep` (`window`), `cwNext` |
| 3 | §5 / 9a.8 "a fetch in the same cycle [as a host program-memory write] returns an undefined word" | Read-before-write: the fetch returns the word as it was before the write. This applies to any address on that core. | 0, the new word, or X. The SPEC does not say. | `Chip.runStep` (cores) |
| 4 | §9 host map: `OUT.OE` exists for all 14 output pins, while `CONFIG_BLOCKS` has `oe` for 8 | A write to `OUT[8..13].OE` is a configuration write: it uses the bank port (sets `BWP` and can delay a following write) but nothing decodes it. | Treat it as unmapped: no bank cycle. | `Config.isCfgAddr`, `Config.out` |

| 6 | §13.2 "its previous level is `RLV` of the previous cycle" | The previous level is `RLV` of the previous cycle (`rlvp`) whenever `RPL` and `EMASK[k]` hold now, even in the first cycle of `RPL`. Setting `RPL` can therefore create an edge from the old `RLV` without any pad edge. `RISE` and `FALL` see the overlay. | Use `sp` in the first `RPL` cycle. | 10 | §13.2 "`POS` advances by 4 per word read" and the read address | `POS += 4` and `BA += 4` when the read is served. A read is requested (`RQ`, visible next cycle) when `!END`, `!RQ`, `!LD` and the buffer is not full (`!(WV && NV)`). The SPEC never says that `BA` advances. | Advance `POS` at the request or at the landing. Request combinationally. Address the word as `START + POS`. | `Util.streamAuto` (replay) |
| 11 | §13.2 two-deep buffer "(`WB`, then `NB`)" with `apply: WB' = NB, WV' = NV, NV' = 0` | `apply` shifts first. A word landing in the same cycle then goes to the first empty slot of the shifted buffer. A word landing in a frozen cycle is stored in the slot that is free at that time, and its valid bit is set in the first unfrozen cycle. | The landing is processed before the shift, or a landing during `apply` goes to `NB`. | `Util.streamAuto`, `streamNext` |
| 12 | §13.2 is silent on `S0.BIT`, `S0.ADV`, `S0.RX` and flush while `RPL` | Same as capture (§12.4): `S0.BIT` reads 0 and the moves have no effect. | Normal §6.3 bit paths during replay. | `streamBit` |
| 13 | §12.3 freeze vs §13.2 replay (the freeze text predates replay) | In a frozen cycle there is no `apply`, `late` or replay request, and `DC` holds, because replay counts as an autonomous stream update. | 14 | §6.3 rewind list (`POS, BIDX, BA, CUR, CV, WV, RQ, LD, PV`) vs §13.2 `NV` | A rewind also clears `NV`. Otherwise a stale `NB` could be applied after a rewind. | Leave `NV` alone, as the literal list does. | `streamNext` |

| 16 | §9 `ERR` list vs §13 (`CWOVR` in `STICKY` bit 2 and `ERRSUM` bit 6) | `ERR` (and so `IRQ`) does **not** include `CWOVR`, exactly as the §9 list reads. | `CWOVR` is a sticky error and raises `IRQ` through `IRQEN[1]`. **Resolved 2026-11-21 (D46): this alternative is correct. SPEC §9 is amended and the Lean follows it.** | `errAny` |
| 17 | §9 "A load in the same cycle as a shifting `SR` is lost" together with "`ADDR' = ADDR + 1` with each load" | The `TX` value is lost but `ADDR` still increments. | A lost load does not advance `ADDR` (and the byte is skipped or retried). | `hostNext` |
| 18 | §13.1 core write queue during a freeze (§12.3 lists only what stops) | **Resolved by D50 (2026-11-21, user decision):** the queue holds while frozen (no bank or runtime drain), matching the RTL (`CoreQueue` cut) and the Python model; SPEC_V2 §12.3 and §13.1 amended. Earlier reading: kept draining. | (was) the queue holds while frozen | `cwNext` (`frozen`) |
| 19 | §13.1 a new host configuration write while `HH` is pending | Not reachable (host writes are at least one SPI byte apart). Lean performs `HH` and holds the new write in `HH`. | Drop the new write. | `cwNext` |
| 20 | §5 program memory output ("its word is at the memory output during t+1") when no address is presented; §6.2 RAM output likewise | Both outputs hold their last read word when no read is presented. A program write without a fetch does not change the program memory output. | The output becomes undefined or 0. This matters only for the §12.3 landing exception and stale reads. | `coreNext`, `runStep` |
| 21 | §9 coincident link events: a register load and a RAM landing in one cycle; an address byte completing while a stale RAM read lands; a load together with an `ADDR` increment from a write; a load and the 8th `SR`; a load while CS_N is high | The register load wins over the RAM landing. Setting address byte 1 or 2 wins over an increment. A write and a load in one cycle increment `ADDR` once. A load wins over the 8th (non-shifting) `SR`. CS_N high clears `TX` and the load is lost, but `ADDR` still increments. | Other priorities. None of these is reachable with a well-formed host at clk/16 except a slow RAM read. | `hostNext` |

## Readings that are literal but surprising (no marker needed, recorded for review)

- §3.4: the start rule `FIRED'[k] = … (Tk <= PH')` uses the final `PH'`, which includes a host `PHASE` write in the same cycle. The rule also covers starts by `Lk.CTL` moves and host `CTL` writes (`RUN' && !RUN`).
- §3.2 with `FOLLOW = 1`: `SC' = 0` in every cycle, frozen cycles included.
- §8: an unbound pin has `idx = 0`, so it drives `LUT[0]` and `OE[0]`, not a constant 0.
- §4: a doorbell to a thread with `EN = 0` is lost (`trig = EN && (…)`). The same applies to a doorbell delivered after a freeze.
- §12.4: with a `LEN` that is not a multiple of 4, `END` is never reached and `POS` wraps at 12 bits.
- §6.1 (v1): a P0 fetch reads `mem[PTR]` with `PTR` as of the serving cycle, not the request cycle.

## Not modelled

- §12.5 (contract violation recording) is a model diagnostic, outside the machine step.
- §10 and the "Consequences" paragraphs are calculated statements, not behaviour. They are candidates for theorems (workstream E).
- Physical timing, pads and the 60 MHz clock are not modelled. The machine-level step is cycle-accurate only.
